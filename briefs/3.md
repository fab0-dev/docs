# Brief: the ledger reference matches the core schema and resolver

## Intent

`docs/reference/ledger.md` must let a developer open any file in `work/{run}/ledger/`, tell whether it is an attempt entry or a gate entry, and know what each field means, when it is present, and how each hash in it was computed. It must also say exactly when the resolver hands out a new attempt and with what number. Where the core plugin looks wrong and the page right, the gap goes to fab0-dev/fab0 as a Story, not into the page.

## Readers

- **A developer debugging a run.** They know the glossary and the wiring (stages, artifacts, gates) and have a ledger file open. They want to know why `next` handed out attempt 3, why an input counts as changed, or why the resolver refuses to read an entry. They need exact rules they can check by hand, for example by recomputing a hash.
- **A fab0-core maintainer or plugin author.** They change the resolver or the schemas, or write tools that read ledgers. They need the full contract of an entry: field sets, naming, hashing and read rules.
- **The docs reviewer.** They check the page line by line against `ledger-entry.json`, `review.json` and `fab0-resolve` at the pinned commit.

Nobody reads this page to learn why fab0 keeps a ledger. That is in [artifacts and the ledger](../docs/explanation/artifacts-and-ledger.md), which already links to the reference (`docs/explanation/artifacts-and-ledger.md:69@a8289d3`) and stays out of scope.

## Findings

Line numbers in `fab0-resolve` are at `c7bd1ff`. Line numbers in `ledger.md` are at `a8289d3`.

**F1. The implicit `pr-review` input is missing.** The page says `inputs` maps "Input artifact → `sha256:<hex>` at hand-out time" (`docs/reference/ledger.md:24@a8289d3`). The resolver adds a `pr-review` key to every attempt's `inputs` whether or not the stage declares it (`plugins/fab0/bin/fab0-resolve:1216@c7bd1ff`). It also skips any declared input whose location is `github: pr-review`, so such an input never appears under its own artifact name (`fab0-resolve:1072-1073@c7bd1ff`). Fix: docs.

**F2. Not every hash is a hash of file bytes.** The page lists only files and directories (`docs/reference/ledger.md:34-35@a8289d3`). The resolver hashes three other kinds of value:

- An `issue-body` input is the issue body with CRLF turned into LF, encoded as UTF-8 (`fab0-resolve:75-76,1070-1071@c7bd1ff`).
- Inside a `foreach`, the input named after the `foreach` artifact is the hash of the task element, not of the file. The element is serialised as JSON with sorted keys, `,` and `:` separators and no ASCII escaping, then encoded as UTF-8 (`fab0-resolve:71-72,1068-1069@c7bd1ff`).
- `pr-review` hashes the same canonical JSON of the sorted list of ids of the reviews that ask for rework (`fab0-resolve:1003-1012@c7bd1ff`).

Fix: docs.

**F3. The directory hash line is ambiguous.** The page gives the line as `relpath\0sha256(file)\n` (`docs/reference/ledger.md:35@a8289d3`). In the code, the per-file hash in the line includes the `sha256:` prefix (`fab0-resolve:67-68,85@c7bd1ff`). Lines are sorted by relative path. A directory with no files counts as missing (`fab0-resolve:656-671@c7bd1ff`). Every value in the ledger has the form `sha256:` plus 64 lowercase hex digits (`ledger-entry.json:39@c7bd1ff`), which the page shows only as `sha256:<hex>`. Fix: docs.

**F4. The `return` key in `verify` is missing.** The page says `verify` maps "Artifact → `pass`, or a list of errors" (`docs/reference/ledger.md:26@a8289d3`). `record` writes one key per declared output, and the value is `<path> is missing` when the output is absent. It also writes a `return` key with the schema errors when the agent's return is invalid (`fab0-resolve:2096-2104,526@c7bd1ff`). Fix: docs.

**F5. `outputs` covers only outputs that exist.** The page says `outputs` maps "Output artifact → `sha256:<hex>`" (`docs/reference/ledger.md:25@a8289d3`). `record` hashes each output from the working tree of its repository at record time and leaves out outputs that don't exist (`fab0-resolve:2097-2100@c7bd1ff`). Fix: docs.

**F6. Attempt entries and gate entries have different field sets.** The page has one table, and its "Required" column follows the schema (`docs/reference/ledger.md:16-30@a8289d3`; `ledger-entry.json:5@c7bd1ff`). What `record` writes (`fab0-resolve:2074-2117@c7bd1ff`):

- **Attempt entry.** `stage`, `task` (only with `--task`), `attempt`, `actor`, `model`, `branch`, `inputs`, `outputs`, `verify` and `gate: {type}` are always present. `gate.type` is the stage's gate, and is `agent` for a stage with an agent gate, without a `decision`. `summary` is present only when the return is valid. `questions` is present only when the return is valid and has questions.
- **Gate entry.** `stage`, `task`, `attempt` (the attempt it judged), `actor`, `model`, `gate: {type: agent, agent, decision}` and `review`. It has no `branch`, `inputs`, `outputs`, `verify`, `summary` or `questions`.

The page also has three smaller errors:

- `model` is the model name that the stage's (or the gate's) model class maps to in `models.claude-code` (`fab0-resolve:1213,1274@c7bd1ff`). The page doesn't say this.
- `actor` is the user given with `--as`, or the `gh` login, when `next` handed the attempt out (`fab0-resolve:1940,1948,2078@c7bd1ff`). It is not the user who ran `record`.
- `summary` is called "the agent's one-paragraph summary" (`docs/reference/ledger.md:28@a8289d3`). Nothing in `return.json:9@c7bd1ff` limits it to one paragraph.

Fix: docs.

**F7. The `review` object isn't described.** The page lists `decision`, `reasons`, `findings` and `unmet` (`docs/reference/ledger.md:30@a8289d3`). The source requires `decision` and `reasons`. Each finding has a required `message` and optional `check` and `location`. `unmet` holds the ids of unmet scenarios or requirements (`review.json:5-24@c7bd1ff`). `record --gate` refuses a review that doesn't validate (`fab0-resolve:2082-2086@c7bd1ff`). Fix: docs.

**F8. The naming rule and its enforcement are missing.** The page gives the patterns (`docs/reference/ledger.md:7-12@a8289d3`). The code builds the name from the entry: `-<task>` only when `task` is set, and `-gate` exactly when `gate` has a `decision` (`fab0-resolve:741-744@c7bd1ff`). On read, an entry whose file name differs from that name is invalid (`fab0-resolve:697-703@c7bd1ff`). Fix: docs.

**F9. The read rules are missing.** The page says nothing about how entries are read. The resolver (`fab0-resolve:622-627,676-705@c7bd1ff`):

1. Reads `work/{run}/ledger/*.yaml` from the base branch first, then the working tree, then the run's branches: local before `origin/`, named `<stage>/<run>-…`. Branches of nested child runs are excluded.
2. Keeps the first copy of each file name, so an entry that is on the base wins.
3. Validates each entry against `ledger-entry.json` and checks its name. On any failure, the command fails with exit code 1 and `invalid ledger entry <path> on <ref> in <repo>`.

The base is `origin/<base>` when it is at or ahead of the local branch (`fab0-resolve:599-613@c7bd1ff`). Fix: docs.

**F10. "Where the stage ran" and "never edited" are vague.** The page says entries are kept "in `work/{run}/ledger/` of the repository where the stage ran. Only `fab0-resolve record` writes these files, and they are never edited" (`docs/reference/ledger.md:3@a8289d3`). The rules in the code:

- The ledger repository is the first repository in the stage's `repos.write`. Without `repos.write`, it is the task's repository inside a `foreach` and `home` outside one. A gate entry goes to the same repository as the attempt it judged (`fab0-resolve:1031-1036,1273@c7bd1ff`).
- `record` refuses with exit 4 unless `next` handed the stage out first, and refuses when a file of that name already exists (`fab0-resolve:2047-2053,2119-2123@c7bd1ff`).
- "One YAML file per agent-stage attempt" leaves out gate entries.

Several pull requests per stage are Planned (step B.2). Fix: docs.

**F11. The new-attempt rule is incomplete.** The page's only rule is "An output is stale when any input hash differs from the one recorded" (`docs/reference/ledger.md:36@a8289d3`). `eval_agent` (`fab0-resolve:1558-1625@c7bd1ff`) works on the latest attempt `n` of a stage and task:

- No attempt yet: attempt 1.
- Attempt `n+1`, with all the reasons it applies in its brief, when any of these holds, even after the attempt was merged:
  - a current input hash differs from the recorded one;
  - an output's hash at the attempt's source differs from the recorded one, because someone edited or removed the output;
  - a `verify` value isn't `pass`.
- Otherwise, the stage is satisfied if the entry is on the base.
- Otherwise, attempt `n+1` when the open pull request's review hash differs from `inputs.pr-review`.
- Otherwise, questions mean a wait, not a new attempt.
- With an agent gate:
  - no gate entry for `n` hands out the gate;
  - `approve` satisfies the stage;
  - `reject` gives attempt `n+1` while the stage's total rejects are at most 2 (`MAX_REWORK`, `fab0-resolve:50@c7bd1ff`), and then escalates to a person;
  - `escalate` goes to a person.

An input is hashed at its current version: where its producer's latest attempt is, otherwise the base (`fab0-resolve:1054-1062@c7bd1ff`). Missing inputs block the stage instead (`fab0-resolve:1564-1570@c7bd1ff`). Fix: docs.

**F12. `code`: `ledger-entry.json` doesn't enforce the two entry shapes that the page and `record` describe.** The page says `agent` and `decision` belong to an agent gate entry, and that `review` holds `decision`, `reasons`, `findings` and `unmet` (`docs/reference/ledger.md:27,30@a8289d3`). The schema accepts entries that break this (`ledger-entry.json:22-34@c7bd1ff`):

- `gate.decision` without `type: agent` or `agent`.
- A gate entry with `branch`, `inputs`, `outputs` or `verify`.
- A `review` that is any object, because it doesn't reference `review.json`.

The resolver treats any entry with a `decision` as a gate decision (`fab0-resolve:743,986@c7bd1ff`). As a result, a hand-made `gate: {type: human, decision: approve}` passes validation on read and counts as an agent approval. Proposed Story for fab0-dev/fab0: make the schema a `oneOf` of an attempt entry and a gate entry, with `review` referencing `review.json`. The page documents what `record` writes and doesn't claim that the schema enforces it.

**F13. Out of scope: `execution.md` misstates which reviews count.** "new requested-changes reviews" (`docs/explanation/execution.md:60@a8289d3`) is narrower than the code, which also counts `COMMENTED` reviews that have a body (`fab0-resolve:51,1010@c7bd1ff`). Issue #3 covers only the ledger reference, so no task here. File it as a separate Docs issue. The ledger reference states the exact rule.

## Outline

One page changes: `docs/reference/ledger.md`, a **reference** page. It describes an entry in the order of the entry itself, and every line can be checked against the sources above. No new pages are needed, so `docs/index.md` is unchanged. The link from the explanation page already exists.

`# Ledger reference`

- Opening paragraph: what the ledger holds (attempt entries and gate entries), the schema `ledger-entry.json`, and a link to [artifacts and the ledger](../docs/explanation/artifacts-and-ledger.md) for the reasons.
- `## Where entries are kept`: path `work/{run}/ledger/`, the ledger repository rule, gate entries beside their attempt. Several pull requests per stage are **Planned (step B.2)** (F10).
- `## How entries are written`: only `record`, only after `next` handed the stage out, refusal when the name exists (exit 4), and which commit the orchestrator makes for each kind of entry (F10).
- `## File names`: the name built from the entry, `-gate` exactly when `gate.decision` is present, unpadded attempts from 1, examples (F8).
- `## Attempt entries`
  - `### Fields`: a table with the columns Field, Present, Meaning, covering every property of `ledger-entry.json` as an attempt entry uses it, including `inputs` keys (`pr-review`, the `foreach` artifact key, skipped `github: pr-review` inputs), `outputs` only for outputs that exist, `verify` with `return` (F1, F4, F5, F6).
  - `### Example`: an entry valid against the schema, with made-up names (Story `#412`, `po-user`).
- `## Gate entries`
  - `### Fields`: the gate entry's field set (F6).
  - `### The review`: every property of `review.json`, with the properties of a finding (F7).
  - `### Example`.
- `## Hashes`: the value format, then a table of what is hashed for each kind of input or output: file, `dir`, `issue-body`, `foreach` element, `pr-review` (F2, F3).
- `### Which version is hashed`: inputs at hand-out time from the current version, outputs at record time from the working tree (F5, F11).
- `## How the resolver reads the ledger`: sources and their order, first name wins, validation and name check, the error and exit code (F9).
- `## When a new attempt starts`: the rule as an ordered list, the attempt number, the cases that don't start one (merged and current, questions, approve, escalate, the reject limit) (F11).

## Acceptance

- **A1.** Every property of `ledger-entry.json`, including `gate.type`, `gate.agent` and `gate.decision`, appears in `docs/reference/ledger.md`. For each one, the page says whether it is present on an attempt entry and on a gate entry, and when.
- **A2.** Every property of `review.json` appears in `docs/reference/ledger.md`, including `check`, `message` and `location` of a finding, with which ones are required.
- **A3.** From the page alone: in which repository and directory are the entries of a stage kept, both inside and outside a `foreach`, and where does a gate entry go?
- **A4.** From the page alone: what is the file name of a given entry, when does a name end in `-gate`, and what happens when a file's name doesn't match its contents?
- **A5.** From the page alone: which keys does `inputs` of an attempt entry have? Why is there always a `pr-review` key, why does an input declared with `github: pr-review` have no key of its own, and what does the key of the `foreach` artifact hash inside a `foreach`?
- **A6.** From the page alone, a reader can recompute each hash: a file, a `dir` (exact line format with the `sha256:` prefix, sort order), an `issue-body` (line endings, encoding), a `foreach` element (exact JSON serialisation), and `pr-review` (which pull request, which reviews count, the value when there is none).
- **A7.** From the page alone: when and from which version is an input hashed, when and from where is an output hashed, and what is recorded when an output is missing?
- **A8.** From the page alone: which keys can `verify` have, including `return`, and what values?
- **A9.** From the page alone: from which branches and in what order does the resolver read ledger entries? Which copy wins when the same file name is in several, and what happens when an entry is invalid?
- **A10.** From the page alone: given the latest attempt of a stage, when does the resolver hand out a new attempt, with what number, and when does it instead wait, hand out the gate, escalate or treat the stage as satisfied? This includes the limit on rejects and the fact that changed inputs reopen a merged attempt.
- **A11.** From the page alone: who writes entries, what `record` refuses, and why an entry is never changed after it is written.
- **A12.** The page has one example attempt entry and one example gate entry. Each is valid against `ledger-entry.json` at `c7bd1ff`, is named by the naming rule, and uses made-up names.
- **A13.** The page is a reference page throughout. Each statement can be checked against `ledger-entry.json`, `review.json` or `fab0-resolve` at `c7bd1ff`, the Planned item carries its roadmap step, and the claim "one-paragraph summary" is gone.
