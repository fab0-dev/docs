# Brief: run 8, choose how a pipeline uses git

## Intent

A person building a factory must decide, for each pipeline, whether its units land on a run branch or straight on the base branch, whether it needs a ledger branch, and what `git.auto_merge` must allow. Today that decision is spread across the branching explanation and the project reference. Add one how-to that walks through the three decisions and ends with the settings for each case, linking the explanation and the reference instead of repeating them.

## Readers

- **A factory builder** who has built a factory or taken an example, knows pipelines, steps, gates and `fab0.yaml`, and is now wiring a new pipeline. They want to know which `git` and `ledger` settings to write, and what each choice will do to their base branch and their reviews.
- **A factory builder adding a second pipeline** of a different kind, such as a triage pipeline next to a delivery one. They want to know whether to override `git` in the pipeline file, and what stays project-wide.

## Findings

**F1.** The explanation puts the ledger branch under "Flat branching", as if it belonged to `flat`.

- Docs: `docs/explanation/branching.md:21-25@18ee160` gives the ledger branch as the second paragraph of the "Flat branching" section.
- Source: `core:plugins/fab0/lib/fab0_engine/schedule.py:131-132@a9862a6` uses `ledger.branch` for any pipeline whose steps write no files, whatever its branching; `core:plugins/fab0/lib/fab0_engine/wiring.py:312-319@a9862a6` still requires `git.run-branch` for such a pipeline under `run` branching.
- Fix: docs (T2).

**F2 (`code`).** Under `flat` branching, `apply` merges into the base branch without the merge policy.

- Docs: `docs/explanation/gates.md:51@18ee160` says merges happen only through `apply`, "within the policy above", and people; `gates.md:24@18ee160` says the policy allows run branches only unless a project allows its base branch.
- Source: `core:plugins/fab0/lib/fab0_engine/apply.py:200-209@a9862a6` checks `git.auto_merge` only for `merge: auto`; a unit with gate `none`, or a human gate decided by a label (`schedule.py:902-904@a9862a6`), merges into its parent unchecked, and under `flat` that parent is the base branch. `wiring.py:537@a9862a6` lets both gates through `validate`. This contradicts `core:plugins/fab0/skills/github/SKILL.md:13@a9862a6` ("Never merge into the base branch … unless the pipeline's `git.auto_merge` allows otherwise") and `product:CLAUDE.md:40@b5816a5`.
- Fix: a code change in `fab0-core` (refuse those gates under `flat` without `allow_base`, or check them in `apply`). A docs task can't fix it. Until then the how-to describes the behaviour as built and warns about it (see Open questions).

## Outline

### `docs/how-to/choose-git-workflow.md` (how-to, new)

Title: "Choose how a pipeline uses git". One short paragraph: the goal is the `git` and `ledger` settings for one pipeline; links [branches and merges](../explanation/branching.md) for how it works and the [project reference](../reference/project.md#git) for the fields.

1. **Decide where accepted work lands.** A table of `run` and `flat`: what each gives, what each costs, which factory suits it.
   - `run`: the whole run reviewed in one pull request into the base branch; units read what was merged before them; `apply` may merge reviewed units with the default policy; the base branch can require pull requests. Costs: work reaches the base branch only when the run's pull request merges; the pipeline needs `git.run-branch` and usually `pr.open-run`, `git.sync-base` and `pr.ready`. Suits delivery factories (the `story` example).
   - `flat`: each accepted unit is on the base branch at once, and the next unit reads it; `git.*` and `pr.*` actions do nothing. Costs: no run-wide review; every `apply` merge lands on the base branch, including gate `none` and label-decided human gates, which `git.auto_merge` doesn't govern (F2); a ruleset that requires pull requests on the base branch refuses `apply`'s merges. Suits pipelines whose units are independent, and pipelines that write no files.
2. **Check whether the pipeline writes files.** If no step writes a repository or a `file` artifact, the run opens no pull request: set `ledger.branch` in `fab0.yaml` (project-wide, not in the pipeline's `git`), a branch nothing else uses, for example `fab0/ledger`. `validate` refuses the pipeline without it. Pair it with `flat`, as the `triage` example does, because `run` branching still requires `git.run-branch`. On the ledger branch nothing merges, so `git.auto_merge` doesn't apply.
3. **Decide what `apply` may merge.** Per choice: `run` with `merge: auto` needs `into: [run]` (the default); `flat` with `merge: auto` needs `into: [base]` and `allow_base: true`; `pr.merge` needs the same; leave `merge: auto` off on a ledger-branch pipeline, since approval already decides and `validate` still checks the target. What `validate` says when the policy doesn't allow a gate.
4. **Write the settings.** One YAML block per case, each with a sentence on what it gives:
   - a `run` pipeline, defaults spelled out;
   - a `run` pipeline whose run `apply` merges into the base branch with `pr.merge`;
   - a `flat` pipeline with human-merged units;
   - a pipeline that writes no files: `flat` plus `ledger.branch`;
   - one pipeline that differs from the project: its own `git` block.
5. **Validate.** Run `fab0-resolve validate`, and what to change for each refusal named above.
