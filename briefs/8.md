# Brief: run 8, choose how a pipeline uses git

## Intent

A person building a factory must decide, for each pipeline, whether its units land on a run branch or straight on the base branch, whether it needs a ledger branch, and what `git.auto_merge` must allow. Today that decision is spread across the branching explanation and the project reference. Add one how-to that walks through the three decisions and ends with the settings for each case, linking the explanation and the reference instead of repeating them.

## Readers

- **A factory builder** who has built a factory or taken an example, knows pipelines, steps, gates and `fab0.yaml`, and is now wiring a new pipeline. They want to know which `git` and `ledger` settings to write, and what each choice does to their base branch and their reviews.
- **A factory builder adding a second pipeline** of a different kind, such as a triage pipeline next to a delivery one. They want to know whether to override `git` in the pipeline file, and what stays project-wide.

## Outline

### `docs/how-to/choose-git-workflow.md` (how-to, new)

Title: "Choose how a pipeline uses git". One short paragraph: the goal is the `git` and `ledger` settings for one pipeline; it needs fab0 0.6.1 or later, where merges into the base branch obey `git.auto_merge` for every gate. Link [branches and merges](../explanation/branching.md) for how it works and the [project reference](../reference/project.md#git) for the fields.

1. **Decide where accepted work lands.** A table of `run` and `flat`: what each gives, what each costs, which factory suits it.
   - `run`: the whole run reviewed in one pull request into the base branch; units read what was merged before them; `apply` merges accepted units into the run branch under the default policy; the base branch can require pull requests. Costs: work reaches the base branch only when the run's pull request merges; the pipeline needs `git.run-branch` and usually `pr.open-run`, `git.sync-base` and `pr.ready`. Suits delivery factories (the `story` example).
   - `flat`: each accepted unit is on the base branch at once, and the next unit reads it; `git.*` and `pr.*` actions do nothing. Costs: no run-wide review; by default a person merges every unit's pull request, because every merge targets the base branch; letting `apply` merge needs `allow_base` and a base branch it may push to. Suits pipelines whose units are independent, and pipelines that write no files.
2. **Check whether the pipeline writes files.** If no step writes a repository or a `file` artifact, the run opens no pull request: set `ledger.branch` in `fab0.yaml` (project-wide, not in the pipeline's `git`), a branch nothing else uses, for example `fab0/ledger`. `validate` refuses the pipeline without it. Pair it with `flat`, as the `triage` example does, because `run` branching still requires `git.run-branch`. On the ledger branch nothing merges, so `git.auto_merge` doesn't apply.
3. **Decide what `apply` may merge.** Per choice:
   - `run`: `apply` merges gate `none` and label-decided units into the run branch; `merge: auto` needs `run` in `into` (the default).
   - `flat`: without `into: [base]` and `allow_base: true`, a unit with gate `none`, a label-decided human gate or `merge: auto` waits, and a person merges its pull request; `validate` refuses `merge: auto` unless `into` holds `base`. With both, `apply` merges them by pushing to the base branch, so a ruleset that requires pull requests there must let the fab0 login bypass it, or `apply` fails. Units inside a gated block merge into the block's branch either way.
   - ledger branch: leave `merge: auto` off, since approval already decides and `validate` still checks the target.
   - `pr.merge` (under `run` only; it does nothing under `flat`): needs `into: [base]` and `allow_base: true`.
4. **Write the settings.** One YAML block per case, each with a sentence on what it gives:
   - a `run` pipeline, defaults spelled out;
   - a `run` pipeline whose run `apply` merges into the base branch with `pr.merge`;
   - a `flat` pipeline where a person merges each unit's pull request;
   - a `flat` pipeline where `apply` merges ungated, label-gated and `merge: auto` units into the base branch;
   - a pipeline that writes no files: `flat` plus `ledger.branch`;
   - one pipeline that differs from the project: its own `git` block.
5. **Validate.** Run `fab0-resolve validate`, and what to change for each refusal named above.
